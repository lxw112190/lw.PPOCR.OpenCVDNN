# v1.0.0-rc.3 Windows 本机性能报告

测试时间：2026-08-01（UTC+8）  
测试版本：`lw.PPOCR.OpenCVDNN v1.0.0-rc.3`  
后端：OpenCV DNN 5.0.0，CPU 推理  
发布包 SHA-256：`cf28df41a68f2ef89bea7746584e2372694e35676b6bfcc2505e91223752b7b4`

## 结论摘要

- 本机完整 OCR 的低延迟配置是 `engine_instances=1`、并发 1：吞吐
  `6.17 req/s`，客户端 P50/P95/P99 分别为 `159.21/177.97/190.76 ms`。
- 完整 OCR 使用 2 个引擎、并发 2 时吞吐提高到 `6.98 req/s`，比单引擎提高
  `13.2%`，但 P95 增加到 `336.50 ms`，热身后 RSS 约从 `153 MB` 增加到
  `287 MB`。4 个引擎发生明显 CPU 争用，不适合作为本机完整 OCR 的默认配置。
- 对已经裁剪好的单行文字，仅识别接口在单引擎、并发 1 时达到
  `126.14 req/s`，客户端 P50/P95 为 `7.63/9.39 ms`。
- 仅识别使用 2 个引擎、并发 2 时达到 `172.69 req/s`；4 个引擎、并发 4
  达到 `199.80 req/s`，但热身后 RSS 约 `551 MB`，需要按吞吐和内存取舍。
- 1000 次多尺寸、并发 4 稳定性测试全部成功。RSS 从 `209.79 MB` 到
  `212.11 MB`，净增长 `2.32 MB`，峰值 `255.51 MB`；异常输入后正常 OCR
  恢复成功。该结果没有发现持续内存增长迹象，但 RSS 测试不能替代 ASan/UBSan。

## 测试环境

| 项目 | 配置 |
| --- | --- |
| CPU | AMD Ryzen 7 7735H with Radeon Graphics |
| CPU 核心 | 8 物理核心 / 16 逻辑处理器 |
| 内存 | 16 GB（系统可见约 15.24 GiB） |
| 操作系统 | Windows 10 Enterprise 22H2，Build 19045，AMD64 |
| 电源计划 | 平衡 |
| Python 客户端 | 3.12.7 |
| OCR 模型 | PP-OCRv6 Tiny Chinese |
| HTTP 传输 | `127.0.0.1`，keep-alive，二进制图片 body |
| 日志 | 基准期间关闭，避免文件 I/O 干扰 |
| HTTP 工作线程 | 4；并发 4 场景保持 4 个常驻工作线程 |

测试的是解压后的正式 Windows x64 部署目录，不是 CMake 构建目录。服务进程、
HTTP 客户端和其他桌面程序共享同一台机器，没有绑定 CPU 核心，也没有切换到高性能
电源计划，因此结果更接近日常桌面部署，不代表实验室环境的极限值。

## 测试方法

每个场景都重新启动服务。每种工作负载先执行 10 次并发预热，确保参与测试的所有
引擎实例完成 OpenCV DNN 延迟分配，然后正式采集 100 次请求。

测试脚本同时记录：

- 客户端端到端耗时：HTTP 发送、服务排队、解码、推理、JSON 序列化和响应读取；
- 服务端 `server_total_ms`：服务接收请求后的内部总耗时；
- 整组请求的吞吐量；
- 服务进程工作集 RSS 的开始值、结束值和峰值。

两种固定输入：

| 工作负载 | 接口 | 图片 | 说明 |
| --- | --- | --- | --- |
| 完整 OCR | `POST /api/ocr` | 500×500 JPEG，46,855 字节 | 包含 16 个文字区域，执行检测、方向分类和识别 |
| 仅识别 | `POST /api/recognize` | 301×57 PNG，26,432 字节 | 已裁剪单行文字，跳过检测 |

## 完整 OCR 结果

客户端延迟包含引擎等待时间，因此它能够反映客户实际观察到的响应时间。

| 引擎数 | 并发 | 吞吐 req/s | 客户端平均 ms | P50 ms | P95 ms | P99 ms | 最大 ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 6.171 | 161.870 | 159.214 | 177.967 | 190.755 | 191.656 |
| 1 | 4 | 6.364 | 618.007 | 623.909 | 648.533 | 676.022 | 676.193 |
| 2 | 2 | 6.983 | 285.779 | 285.306 | 336.503 | 385.634 | 415.817 |
| 2 | 4 | 6.922 | 570.960 | 574.855 | 680.932 | 704.900 | 705.817 |
| 4 | 4 | 6.516 | 608.110 | 604.444 | 761.512 | 791.278 | 792.987 |

单引擎并发从 1 增加到 4，吞吐仅增加约 `3.1%`，平均延迟却接近四倍。这符合
“一个引擎同一时刻只执行一个请求”的设计：排队不会创造计算能力。2 个引擎提供了
本机完整 OCR 的最高实测吞吐；增加到 4 个引擎后，CPU、内存带宽和 OpenCV 内部
线程发生竞争，吞吐反而下降约 `6.7%`。

客户端与服务端平均耗时差通常约 1～2 ms，说明回环 HTTP、二进制传输和 JSON
封装不是这组完整 OCR 工作负载的主要瓶颈。

## 裁剪文字仅识别结果

| 引擎数 | 并发 | 吞吐 req/s | 客户端平均 ms | P50 ms | P95 ms | P99 ms | 最大 ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 126.141 | 7.850 | 7.628 | 9.392 | 11.116 | 11.117 |
| 1 | 4 | 136.654 | 28.668 | 28.471 | 31.454 | 39.763 | 41.007 |
| 2 | 2 | 172.693 | 11.478 | 11.329 | 13.682 | 18.742 | 21.785 |
| 2 | 4 | 166.678 | 23.585 | 23.273 | 29.433 | 37.192 | 40.271 |
| 4 | 4 | 199.797 | 19.584 | 19.606 | 24.324 | 28.020 | 28.162 |

仅识别跳过检测模型，单请求速度约为完整 OCR 的 20 倍。2 个引擎相比单引擎吞吐
提高约 `36.9%`，同时仍保持较低的尾延迟，是本机裁剪文字识别较平衡的配置。4 个
引擎可以继续提高总吞吐，但每个请求的 P95 从 `9.39 ms` 增加到 `24.32 ms`。

## 引擎数量与内存

`initialized RSS` 是服务开始监听、尚未完成真实图片推理时的工作集；OpenCV DNN 会
在首次推理时延迟分配中间缓冲区，因此容量规划应使用热身后的 RSS。

| 引擎数 | 开始监听 RSS MB | 完整 OCR 热身后 RSS MB | 完整 OCR 峰值 MB | 仅识别结束 RSS MB |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 23.39～23.45 | 149.33～149.71 | 151.90 | 153.55 |
| 2 | 31.79～31.80 | 281.05～281.38 | 310.91 | 286.64 |
| 4 | 48.50 | 546.45 | 600.43 | 550.70 |

本机每增加一个完全热身的引擎，大约增加 130 MB 量级的常驻内存。峰值还会受到输入
尺寸、检测候选框和同时执行请求数影响，生产环境不能只按表中的固定样图预留内存。

服务从进程创建到 `/health` 就绪约为 `506～516 ms`。此时模型图已经加载，但尚未
分配全部首次推理缓冲区。

## 1000 次稳定性测试

稳定性测试使用 1 个引擎、4 个并发客户端，交替发送 64×32、320×180、960×540、
2048×1536 图片以及仅识别请求。正式循环后又覆盖 10 类异常输入，并发送正常请求
验证恢复。

| 指标 | 结果 |
| --- | ---: |
| 完成请求 | 1000 / 1000 |
| 并发数 | 4 |
| RSS 基线 | 209.79 MB |
| RSS 结束 | 212.11 MB |
| RSS 峰值 | 255.51 MB |
| RSS 净增长 | 2.32 MB |
| 异常输入恢复 | 通过 |
| 最终状态 | 通过 |

峰值 RSS 高于固定 500×500 样图基准，是因为稳定性测试包含 2048×1536 的解码与检测
工作负载。结束值回落到接近基线，未观察到随请求次数持续增长的现象。

## 本机推荐配置

通用完整 OCR、优先低延迟：

```json
{
  "engine_instances": 1,
  "worker_threads": 4,
  "max_queued_requests": 32,
  "engine_wait_timeout_ms": 5000
}
```

完整 OCR、愿意用约两倍模型内存换取有限吞吐提升时，可使用
`engine_instances=2`，并把客户端有效并发控制在 2 左右。本机不建议为完整 OCR
配置 4 个引擎。

以裁剪文字仅识别为主时，建议从 `engine_instances=2`、并发 2 开始。只有明确需要
接近 200 req/s 的小图识别吞吐，并能接受约 550 MB 热身工作集和更高尾延迟时，才考虑
4 个引擎。

`worker_threads` 和队列长度只影响请求承载与等待方式，不会增加推理算力。持续流量
超过上述稳定吞吐时，应让服务及时返回 `429/503`，由客户端退避或扩展服务实例，
而不是无限增加等待队列。

## 适用范围与限制

- 本报告只代表上述 CPU、系统、电源计划、模型和固定输入，不应直接外推到其他机器。
- 完整 OCR 性能与图片尺寸、文字区域数量、方向分类和文本长度高度相关。
- 本次使用回环网络和 keep-alive；跨机器网络、TLS、反向代理都会增加额外延迟。
- 测试期间没有模拟其他高 CPU 业务，也没有固定频率或清空系统缓存。
- RSS 回落和低净增长是稳定性信号，不是数学意义上的“无内存泄漏”证明；发布判断还要
  结合 Linux ASan/UBSan CI 和更长的 5000 次定时测试。
